# Getting started

This page takes you from an installed CLI to a committed `asyncapi.yaml` that CI
refuses to let drift.

## 1. Install the CLI

```bash
go install github.com/RubenRibGarcia/asyncgo/cmd/asyncgo@latest
```

`go install` drops the `asyncgo` binary in `go env GOPATH`/bin — usually
`~/go/bin`. Make sure that directory is on your `PATH`.

`asyncgo` reports its build metadata with `asyncgo version`:

```console
$ asyncgo version
devel (commit unknown, built unknown)
```

A binary built by `go install` from `master` and the released archives both say
`devel` unless the release pipeline stamped them, so `devel` tells you the version,
not that something is broken.

!!! note "Prebuilt archives"

    `goreleaser` builds Linux, macOS and Windows archives for `amd64` and `arm64`
    on every version tag and attaches them to the GitHub release. Until the first
    version is tagged, use `go install` as above.

### Alternative: pin the CLI as a module tool

If your module's `go.mod` declares `go 1.24` or newer, you can skip the `PATH`
step and let Go manage the CLI instead:

```bash
go get -tool github.com/RubenRibGarcia/asyncgo/cmd/asyncgo@latest
```

That adds a `tool` directive to your `go.mod`:

```go
tool github.com/RubenRibGarcia/asyncgo/cmd/asyncgo
```

Commit `go.mod` and `go.sum`, then invoke the CLI through the directive — note the
`go tool` prefix on every command:

```bash
$ go tool asyncgo version
asyncgo v0.0.0-20261108234906-108b5f3370eb (built unknown)
```

Unlike a `go install` binary, the tool build reports the pinned module version
rather than `devel`. The trade-offs: the version is reviewed and updated in
`go.mod` like any other dependency (no separate upgrade step, no `PATH` setup),
and CI runs the exact same version without fetching `@latest` at build time.
In exchange, the CLI becomes a module dependency of your module.

## 2. Declare a catalog

Add a file to your module that declares a catalog — a package-level variable of
the type `asyncgo.Spec(...)` returns:

```go
package orders

import "github.com/RubenRibGarcia/asyncgo"

// Catalog is the AsyncAPI description of the orders service.
var Catalog = asyncgo.Spec(
	asyncgo.Info("Orders Service", "1.0.0"),
	asyncgo.Servers(asyncgo.Server("prod", "kafka", "broker.example.com:9092")),
	asyncgo.Channels(
		asyncgo.Channel("order-placed").
			Send(asyncgo.Operation().
				Message(asyncgo.MessageOf(OrderPlaced{}).Name("OrderPlaced"))),
	),
)
```

and a payload struct next to it:

```go
// OrderPlaced is the message emitted when an order is placed.
type OrderPlaced struct {
	OrderID string  `json:"order_id" asyncapi:"required"`
	Amount  float64 `json:"amount"   asyncapi:"required"`
	// Optional note from the customer
	Note string `json:"note"`
}
```

!!! note "The catalog may live in any package of the module"

    `asyncgo` discovers catalogs across the module's packages, then materializes
    them in a small generated harness. Your `main` function is never executed, and
    a catalog does not have to be imported by a `main` package — the document
    describes the module, not one of its binaries. If a `main` package exists but
    imports no catalog, the generator says so and generates anyway.

    The one exclusion is package `main` itself: the harness cannot import a
    program, so a catalog declared there is not generated. Keep catalogs in
    library packages.

!!! note "Nothing is generated by importing the library"

    The DSL never runs in your program. At runtime `Catalog` is an ordinary
    value; the document is produced by the CLI walking your source. Your binary
    gains no dependency on generation.

## 3. Generate the document

From the module root:

```bash
asyncgo generate .
# or, if you installed via the tool directive:
go tool asyncgo generate .
```

```console
$ asyncgo generate .
wrote /home/you/orders/asyncapi.yaml (1 catalog(s))
```

Commit the result. It is the artifact — reviewed in pull requests like any other
code, and diffed by `asyncgo check` like any other generated file.

If the module declares more than one catalog and you would rather commit one
document per catalog than their merge, aim `-o` at a directory instead:

```bash
asyncgo generate . -o docs/
# wrote /home/you/orders/docs/orders.asyncapi.yaml
# wrote /home/you/orders/docs/payments.asyncapi.yaml
```

Each document is then built from its own catalog, keeps its own `info`, and is
named from the catalog (`.Named("orders")`) or from where it is declared. See
[one document per catalog](cli.md#one-document-per-catalog).

The full flag list — `--format`, `-o`/`--output`, `--config` — is on [CLI](cli.md).
One rule matters here: pass the **same** `--format`, `--output` and `--config`
flags to `check` that you pass to `generate`, because `check` compares against
exactly the file `generate` would have written.

## 4. Fail CI when the artifact is stale

```bash
asyncgo check .
# or, if you installed via the tool directive:
go tool asyncgo check .
```

```console
$ asyncgo check .
/home/you/orders/asyncapi.yaml is up to date
```

The exit code is the contract: `check` exits **3** when the artifact is stale and
**1** when the check could not run at all, so CI can tell "regenerate the committed
document" from "the build is broken". The [CLI reference](cli.md#asyncgo-check) has
the full table and the shell idiom for branching on it.

```yaml
- run: go run github.com/RubenRibGarcia/asyncgo/cmd/asyncgo@latest check .
```

Pin a released version (`@v0.1.0`) once one is published rather than tracking
`@latest`. With a committed `tool` directive, the same step resolves the version
from your `go.mod` — no `@latest` lookup, no version pin:

```yaml
- run: go tool asyncgo check .
```

`-v` narrates what the command did — useful when the check says *stale* and you
want to know which settings it used; `-vv` adds per-package detail and a timing
recap. [CLI](cli.md#verbose-logging) has the transcripts.
